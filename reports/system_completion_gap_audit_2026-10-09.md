# FXシステム完成に向けた実装棚卸し・次工程監査
更新日: 2026-10-09
対象リポジトリ: https://github.com/rikuudon24-beep/chair-scale

## 結論
本プロジェクトは「研究だけ」の段階ではない。H4のエントリー監視、建玉の決済条件監視、GitHub Issueによる永続アラート、定期データ更新、データ修復用Workflowが既に存在する。
ただし、現時点で「完成した自動通知システム」とは判定しない。今回の棚卸しで、最終運用前に優先して閉じるべき課題を2つに絞った。

1. **データ品質ゲートの強化**: 現行のOHLC検査と7日超ギャップ検査だけでは、H4の欠損・時刻異常・更新遅延を十分に検知できない。
2. **通知の到達先の確定**: 現在確認できた永続通知先はGitHub Issues。ChatGPTへのプッシュ通知が実装済みとは確認できない。GitHub IssueをChatGPTプッシュと同一視しない。

売買ロジックは、データ品質と通知経路の信頼性が確認できるまで、実運用向けに安易に変更しない。

## 今回確認した既存機能
- `.github/workflows/fx-current-notification-state.yml`: 毎時07分UTCに市場データを増分更新し、完了済みH4のみで状態判定。状態CSVを保存し、エントリー候補をGitHub Issueに発行する設計。
- `.github/workflows/fx-position-exit-monitor.yml`: 毎時17分UTCに登録済み建玉のH4決済条件を判定し、決済アラートをGitHub Issueに発行する設計。
- `.github/workflows/fx-data-incremental.yml`: 平日06:17 JSTにデータ更新・provenance更新・OHLC検査を行う設計。
- `.github/workflows/fx-data-gap-repair.yml` と `scripts/repair_market_gaps.py`: 12ペア×H4/D1の履歴欠損修復を行う仕組みが存在。
- `scripts/monitor_notification_state.py`: 完了済みH4を対象に、固定されたエントリー状態機械を評価する。
- `scripts/monitor_position_exit.py`: 登録建玉に対する独立した決済条件を評価する。どちらも注文執行ではなく通知用。
- H1用の別監視Workflowも存在する。H4/D1監視と同一系統と決めつけず、通知ID・データソース・建玉台帳の競合を確認してから統合する。

## データ品質監査の所見
### 既存レポートの記録
`reports/100pip_data_quality.csv` では、H4データは各ペア約9,212〜9,653行、期間は概ね2021-01-03〜2026-09-18。列 `bad_gaps` は各ペア263〜302と記録されている。D1の同列は0〜3。
ただし、このCSV単体には `bad_gaps` の定義、対象間隔、許容した週末・市場休場の扱いが書かれていない。よって、この数をそのまま「実際の欠損数」と断定しない。

### 現行バリデータの限界
- `scripts/validate_market_data.py`: ファイル存在、行数、OHLC値の妥当性、タイムスタンプの単調増加を検査するが、H4の期待時刻列との照合はしない。
- `scripts/validate_market_coverage.py`: 期間の始終端と7日を超える時刻差を検査する。7日未満の欠損や4時間足単位の異常は、単独では失敗判定にならない。
- したがって、既存の `[OK]` は「全てのH4足が連続している」ことを保証しない。

### 次に実装すべき検査
1. タイムフレーム別に期待されるバー間隔を定義し、週末・流動性休場・DST・配信元の時刻仕様を区別する。
2. 欠損候補を「通常休場」「要確認」「実欠損の可能性」に分類し、時刻差だけで機械的に埋めない。
3. 欠損区間数、期間、ペア、前後のバー、修復の成否をCSV/Markdownで保存する。
4. 監視前にデータ品質ゲートを実行し、重大な欠損・データ鮮度異常があれば売買シグナルを通常アラートとして発行せず、データ異常アラートに切り替える。
5. 修復後に同じ検査を再実行し、修復前後の差分とデータハッシュを記録する。

## 通知システムの完成判定で残る確認
- GitHub Issueの作成は確認できるが、ユーザーが期待するスマートフォンへの通知として安定して届くかは別問題。GitHubアプリの通知設定、Issueの重複防止、通知遅延、失敗時の再試行を実地確認する必要がある。
- ChatGPTへの直接プッシュ通知は、今回見たWorkflow群からは確認できない。現状を「ChatGPTプッシュ通知実装済み」と表現しない。
- エントリー通知は「次のH4始値候補」という時間制約がある。監視実行が遅れたシグナルを有効候補として再通知しないことを、運用テストで確認する。
- 決済通知は `config/active_positions.json` に登録された建玉が対象。ポジションの追加・決済・履歴記録の手順を固定し、実際の保有状況と台帳がずれないようにする。
- エントリーと決済は独立した監視スケジュールだが、共通の建玉ID・ペア・方向・エントリー時刻で結び付け、通知履歴を一つのトレード台帳に統合する必要がある。

## 優先順位
### P0 — システムの誤通知を防ぐ
1. 時刻間隔を認識するデータ品質監査と鮮度チェック。
2. H4エントリー通知の有効期限・重複防止・実行失敗の検査。
3. 建玉台帳と決済通知の整合性チェック。
4. GitHub Actionsの最新実行結果を確認し、定期実行が実際に成功しているかを記録する。

### P1 — 通知を実用化する
1. GitHub Issue通知がスマートフォンに届く運用テスト。
2. 通知を「エントリー候補」「決済候補」「データ異常」「監視失敗」に分類。
3. エントリー・決済・結果を共通IDで結び付けたトレード台帳を作る。

### P2 — 売買優位性の改善
1. 既存の通貨別研究を棚卸しし、未検証の仮説だけを選ぶ。
2. 既存のUSDJPY研究（ブレイク後のリテスト成功/失敗、D1/W1構造、Bull/Bear非対称性）を重複実験せずに活用。
3. Discovery / Validation / OOS、ペア別、ロング/ショート別の基準を満たした候補だけを通知ロジックに入れる。
4. 勝率単独でなく、PF・期待値・最大DD・取引数・スプレッド/スリッページ耐性を判定する。

## 変更管理ルール
- この監査は既存コードと設定ファイルの読み取りに基づく。今回、Workflowを実行したり、実際のスマートフォン通知を受信確認したりはしていない。
- この監査だけを理由に売買ルールを変更しない。
- 新しい調査は既存レポートを検索してから開始し、同じ仮説・同じ期間・同じ指標の重複検証を避ける。
- 以降の変更は、実装差分・テスト結果・GitHub保存先を明示する。

## 判定
**実装済みの構成要素は複数あるが、完成判定は未達。**
最優先は新しいインジケーター探しではなく、データ品質ゲート、実際の通知到達、建玉台帳の整合性を確認し、通知が「正しい・期限内・重複しない」状態にすること。
